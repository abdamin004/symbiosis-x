The workflow that runs the flight

The run starts from a versioned mission package. Navigation tracks the approved plan. Scheduled events and changes from the simulation activate smaller workflows, even on a nominal flight. The flight loop continues when a nonblocking task is waiting for review.

  1. Load run

    Open the mission package

    Freeze route, checkpoints, asset and crew profiles, policies and event fixtures for this run.

  2. Advance

    Move the simulation clock

    Apply due scenario inputs and accepted observations, then deliver due messages. Process equal-time events in stable order.

  3. Dispatch

    Run due workflows

    Navigation, atmosphere, power, crew and Relay react to their configured events and scheduled checks.

  4. Decide

    Apply policy and authority

    Routine work proceeds through approved tools. Protected actions wait for Crew approval and a current-state recheck in Sama’s gate.

  5. Publish

    Update both views

    Record outcomes once. Publish onboard state and queue a filtered Ground snapshot. Update ETA and pending work.

Repeat from Move the simulation clock until the run is paused, completed or terminated. Browser refreshes read projections without advancing the clock. A mission hold can freeze a phase transition while the clock and onboard checks continue.

Nominal flight path

Check readiness → follow the next scheduled leg → advance at the planned checkpoint when prerequisites pass. Minor state changes update the display and tasks. Route changes require a new approved plan revision.

Separate incident path

Subsystem escalates → open one case → compare options → get a decision → apply through the gate → verify → close or keep held. The existing incident canvas documents those branches.

Workflows that run inside the twin

Each workflow owns a piece of ship or crew state. Its trigger, dependency and result identify what the engine runs and what the deck shows. Phase schedules, limits and model fidelity are set by the mission package.

Humans lead, agents handle routine work

Abdelrahman’s Monitor, Planner agent and Relay run inside Sama’s FastAPI service. They use deterministic workflow rules, typed tools and bounded retries. Agents can carry out low-risk work in the simulation on their own. A language model can later explain a decision or organize evidence through the same limited tool interface.

Architecture behind the flight

Python owns the clock, numerical models and deterministic policy. FastAPI serves role-specific projections and accepts typed commands. React with JavaScript/JSX and Tailwind draws the route, deck, workflow status and event history. Virtual sensor samples carry a source, timestamp, unit and quality before the twin aggregates them by component and subsystem. The simulator is the only plant this design operates.

Solid arrows carry observations, events and projections. Dashed arrows carry Crew requests, Ground advice or committed simulator commands. Relay delivers advice to the onboard event workflow. The server enforces role permissions and never builds Ground by hiding fields in a Crew response.

Mission package and incoming data

Map each supplied dataset field to a typed signal with source, unit, time, quality and coverage. Use it to initialize, calibrate or replay only the model it supports. Keep missing fields explicitly unknown or label synthetic defaults. Validate a new package before starting a run. Store package and policy versions with the replay.

One clock, distinct state

Keep simulator state, accepted twin estimates, and delivered Ground snapshots separate. Use journal sequence for order, decision revision for applicability and a snapshot ID for exact evidence. A reset starts a new run. One committed command has one simulator effect, even when retried.

Decisions for the team

Agree on the flight model

Proposed baseline is a preplanned phase-and-waypoint simulator with schedule-based ETA. Give navigation a true state and a phase gate. Add trajectory dynamics when the team has inputs it can validate.

Agree on subsystem depth

Proposed baseline models cabin CO₂ and power headroom. Oxygen, pressure, feeders and stored energy have their own states and workflows. Use explicitly scripted or unavailable signals until those models have evidence.

Agree on agent authority

Proposed baseline lets agents check, assign, route and record. Humans approve consequential simulated changes. Decide which additional routine commands, if any, qualify for a narrow automatic allowlist.

The preview keeps the original drawing’s four crew stations. The team can combine duties and use one individually modeled synthetic profile. The route, ship controls and incident work all use the same mission package and event model.
