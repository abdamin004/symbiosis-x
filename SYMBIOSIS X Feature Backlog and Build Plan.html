Build health and tests with the first slice

These are implementation tickets and planned checks. The probes report whether the application can serve a demo. The ship’s simulated faults stay on the mission dashboard.

Service responds

SX-20A · GET /health/live returns 200 when FastAPI responds. It does not read SQLite, tick the mission clock or require an active run.

Service can start a run

SX-20B · GET /health/ready checks the already initialized SQLite store, expected migration revision and valid golden manifest. Return 200 or 503 with bounded check codes. Reading readiness cannot create a database or mutate a run.

Operator sees the difference

SX-20C · Service status distinguishes starting, ready and unreachable. A scrubber fault, Relay blackout or missing organizer data does not make the app unready.

    Repeat from a clean checkout

    Record commit, scenario version, seed and pass/fail. Hold a failed merge or revert the isolated change and rerun. Tag the revision after the checks pass.

Definition of done and release checks

Before merging a ticket

Name the dependency and affected consumer. Attach the passing fixture or test. Have the named reviewer check the diff. Verify model logic at the API boundary or UI behavior in the actual screen, depending on the ticket. Record known gaps with their own issue.

Before tagging the release

From a clean checkout, verify the entered reading and explanation, both emergency drills, the delayed Ground handoff and private-field exclusion. Rehearse the health fallback.
